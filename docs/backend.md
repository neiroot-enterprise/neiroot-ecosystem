# Правила бэкенда

Обязательные источники: [AGENTS.md](../AGENTS.md), [архитектура](architecture.md), [ядро](core-architecture.md), [требования](requirements.md), [доступ](access-model.md), [контракты](api-contracts.md).

## Стек

Бизнес-сервисы и BFF — Go, HTTP на chi/net/http. У каждого микросервиса собственная логическая PostgreSQL-база, роли доступа и миграции. Python/FastAPI используется для аналитики и AI-сервисов, когда начинается их реализация. Обязательного Go для этих сервисов пользователь не задавал.

Зафиксированы Go 1.27.1, chi 5.3.2, pgx 5.11.0, goose 3.28.0, go-oidc 3.21.0; go.mod/go.sum фиксируют весь граф. Не вводить новую технологию, заменяющую согласованную архитектуру, без обсуждения.

## Модульный монолит

Фактическое размещение Go-кода (единый go.mod, отдельные бинарники):

```text
services/<service>/main.go  # точка входа и composition root
services/core/internal/
  modules/<module>/
    domain/                 # сущности, правила и инварианты
    application/            # сценарии и принадлежащие им порты
    adapters/
      inbound/              # HTTP, обработчики событий по потребности
      outbound/             # БД, файлы и внешние API
internal/platform/          # общая техническая инфраструктура
internal/contracts/         # сгенерированные transport DTO
internal/security/          # независимый Principal
services/<service>/migrations/ # встроенные goose-миграции
```

company/settings имеют домен, сценарии, порты и адаптеры; money/sales резервируют доменные границы, бизнес-сценарии отложены. Домен не импортирует chi, SQL-драйвер, SDK брокера и других сервисов. Порты определяются потребляющим сценарием; адаптеры реализуют их. Не создавать интерфейс для каждой функции, если он не выражает границу.

В ядре четыре модуля из [core-architecture.md](core-architecture.md). Схемы PostgreSQL `money`, `company`, `sales`, `settings` созданы для их разграничения; один модуль владеет своими данными и миграциями. Не выполнять JOIN/запись в таблицы другого модуля в обход внутреннего API. Модуль задач в ядре не создавать.

## HTTP, данные и надёжность

- BFF занимается входом, маршрутизацией и подготовкой ответа для интерфейса; доменная логика находится в профильном сервисе.
- Проверять запросы на границе, а инварианты — в домене. Возвращать ошибки по контракту без внутренних SQL-ошибок и стеков вызова.
- Проверять токен, членство в tenant и разрешение для каждой операции. Объект и связанные ссылки должны принадлежать допустимому tenant.
- Область транзакции определяется сценарием. Бизнес-запись и Outbox — одна транзакция; избегать распределённых транзакций по умолчанию.
- Уникальность и ссылочная целостность подкрепляются ограничениями БД с учётом tenant. Индексы выбираются по реальным запросам.
- Для денег использовать точное представление; валюты, округления и формулы не изобретать.
- Go-код передаёт context, имеет таймауты внешних запросов и корректно завершает фоновые задачи. Размеры пулов и пределы запросов настраиваются по среде.
- События обрабатываются идемпотентно; потеря соединения не должна приводить к потере принятой бизнес-записи.
- Миграции хранить в проекте и запускать воспроизводимо. Автоматический сброс данных при запуске запрещён.

## Диагностика и эксплуатация

В первом этапе включены JSON slog, метрики запросов/ошибок/суммарной длительности, технические проверки liveness/readiness и корреляцию вызовов. Не логировать пароли, токены, содержимое документов и персональные данные без необходимости.

Будущий общий контур мониторинга — OpenTelemetry, Prometheus, Grafana, Loki и Tempo. Детализация модулей и функций добавляется по потребности; для CPU/памяти Go предусмотрен pprof. Диагностические интерфейсы не публикуются в открытый пользовательский API.

Резервирование охватывает PostgreSQL, ClickHouse, файлы, конфигурации и необходимые секреты. Конкретные расписания, хранение и цели восстановления определяются для среды, см. [development.md](development.md). Наличие pgBackRest в UML не означает настроенную рабочую копию.

## Проверка и сдача

Обязательны проверки доменных правил, SQL-адаптеров с PostgreSQL, контрактов и tenant-изоляции на двух экосистемах. Проверять ошибки, повторные события и конфликты только для реально реализуемых сценариев. Фактические команды — [development.md](development.md). Бизнес-события на этом этапе не публикуются, поэтому Outbox/брокер не запускаются.
