# Критерии качества и сдачи

Применяются к согласованному этапу из [mvp.md](mvp.md), не требуют реализовать всю платформу заранее. Порядок разработки определяет пользователь с агентом в [implementation-plan.md](implementation-plan.md).

## Рабочий результат

- Контейнерный стек воспроизводим из общих конфигураций и отдельно документированной персональной подготовки.
- Реальные пользовательские сценарии соответствуют подтверждённым требованиям и API; моки и ещё не реализованные части явно обозначены.
- Изменения сохраняются после перезапуска сервисов; миграции применяются на чистой базе и при обновлении поддерживаемого состояния.
- Интерфейс соответствует референсам, использует общие компоненты и показывает загрузку, ошибки и пустые результаты.
- Доступ, ввод и ошибки понятны пользователю; секреты и реальные клиентские данные не попадают в код и логи.

## Проверки по риску

| Область | Что требуется доказать |
|---|---|
| Домен | Подтверждённые правила и ограничения, включая неуспешные сценарии |
| PostgreSQL | Запись/чтение, ограничения и миграции на реальной тестовой PostgreSQL |
| Tenant | Пользователь экосистемы A не читает и не меняет данные B; нельзя подменить tenant или ссылку на чужой объект |
| Разрешения | Пользователь без нужного разрешения получает отказ даже при прямом запросе к API |
| API | Запросы, DTO и ошибки соответствуют спецификации |
| Интерфейс | Основной сценарий в браузере, ошибки формы, клавиатура, широкий и узкий экран |
| События | Outbox не теряется при сбое; повтор не создаёт двойной результат — когда события входят в этап |
| Переключение экосистемы | Не показываются данные и кеш прежнего tenant — когда переключение входит в этап |
| Восстановление | Данные восстанавливаются из реальной копии — когда резервирование включено в этап |

Не подменять интеграционные проверки тестами, в которых все адаптеры замоканы. Не добавлять тесты, повторяющие каждую строку реализации. Выбирать проверки по фактическим рискам изменения.

## Отчёт агента

В отчёте указать реализованные сценарии, выполненные проверки с результатом и оставшиеся ограничения. Переносимые команды проверок описаны в development.md, команды запуска конкретной машины записываются в .local/docs/development.md. «Сборка прошла» не доказывает бизнес-функциональность и tenant-изоляцию. Для визуальных изменений проверить фактический экран, для изменения контракта — клиент и сервер.

Производительность проверяется относительно согласованных нагрузки и задержек. Выбор Go не заменяет измерения. Пока численные цели не определены, не обещать выдерживаемый RPS и конкретное время ответа.

## Приёмка первого этапа

Реальные PostgreSQL 18.6 и Keycloak 26.8.0 обязательны для проверки входа, обоих подключений, ошибок provisioning, приглашений, прав и tenant-изоляции. Визуальные фикстуры не заменяют эти проверки. Playwright проверяет также узкий экран, клавиатуру и очищение данных при переключении. Сертификат должен быть доверенным, TLS verification не отключается.

Функциональные результаты — [test-report.md](test-report.md). Контейнерные сборки, сохранность данных и чистую установку проверять отдельно. Нативная проверка повторных миграций и restart фиксируется отдельно и не заменяет контейнерную приёмку. Машинные команды и диагностику вести только по правилу персональной рабочей области из AGENTS.md.

## Выбор проверок по изменению

- Документация — ссылки, существование описанных файлов и команд, согласованность с требованиями и текущей реализацией. Изменение документации само по себе не подтверждает новую функциональную приёмку приложения.
- TS/TSX — typecheck и соответствующий пользовательский сценарий. CSS, ресурсы и сборочная конфигурация — production-сборка и применимая визуальная проверка. Общий компонент — также его затронутые применения.
- API, права и данные — проверки контракта, серверных отказов, повторов и tenant-изоляции по фактическому изменению. Требования полной приёмки этапа действуют отдельно.

## Приёмка интерфейса по эталонам

- Для вкладок подразделов сверить [оформление](design/components.md#tabs) и [размещение](design/patterns.md#вкладки-подразделов) с навигацией предприятий: цвета активного пункта совпадают с главным меню в обеих темах, геометрия библиотечного компонента сохранена. Измерить внешние промежутки над и под вкладками. Сверить подложку предприятий с формулой для светлой темы и токеном тёмной темы из каталога компонентов. Проверить клавиатуру, выбранное состояние после перехода и отсутствие переполнения на 390 px; для ссылок — прямой URL и возврат браузером.

- Для фильтров состояния списков предприятий и организаций сравнить с основным примером shadcn Select по [каталогу компонентов](design/components.md#фильтр-состояние): высота 32 px, ширина по самому широкому пункту, стабильная при выборе любого значения, внутренние отступы группы, подпись внутри меню без внешнего дубля и совмещение выбранного пункта с полем. Проверить, что при раскрытии поле и его рамка скрываются без сдвига шапки, а после Escape поле снова видно и получает фокус. Проверить выбор, запрос status и сброс пагинации. Для остальных Select проверить, что при свободном месте снизу список открывается ниже нижней границы поля, не перекрывает выбранное значение, закрывается по Escape с возвратом фокуса и применяет выбранный пункт. Повторить для общих фильтров в использующих их разделах.

- Для пагинации с прокруткой страницы проверить возврат с короткой последней страницы на полную при размере 10: после загрузки нижние стрелки остаются в видимой области. Проверять оба направления и задержанный ответ, особенно на 390 px.

- Для самостоятельного раздела проверить полный [состав заголовка](design/patterns.md#заголовок-раздела): название, короткое описание и доступное по правам главное действие. Сверить содержание описания с назначением раздела, актуальность названия экосистемы и перенос длинного текста на узком экране.

- Сравнить экран с соответствующим примером в docs/design/employees.md или docs/design/app-shell.md при одинаковой ширине и теме. Для однотипных элементов отдельно сверить высоту, типографику, отступы, радиус, иконку и её размер; образцы выбирать по роли элемента. Проверка работоспособности и просмотр нового экрана без сопоставления с эталоном эту проверку не заменяют.
- Проверить светлую и тёмную темы, читаемость текста, контраст фокуса и доступные имена иконок. На ширине 390 px проверить достижимость действий и отсутствие горизонтальной прокрутки страницы.
- Пройти сценарий с клавиатуры, включая открытие и закрытие окна и возврат фокуса.
- Проверить применимые состояния: загрузку, пустой результат, ошибку, повтор, отсутствие прав, несохранённый ввод и успешное действие.
- Просмотреть изменения компонентов: подходящие компоненты должны быть переиспользованы. Для нового элемента проверить, какое поведение отсутствовало в каталоге. Отличать проверенный серверный сценарий от локального прототипа.
- Если изменена общая навигация, открой любой экран с оболочкой приложения. При раскрытом и свёрнутом Sidebar, а также в мобильном меню проверь активный пункт, доступ к профилю и выбор экосистемы с длинным названием. Повтори проверку в светлой и тёмной темах.

- Для постраничного списка сверить общий подвал с эталоном: размер страницы, счётчик и стрелки, фон/рамку/отступы и мобильную раскладку. Проверить запросы limit/offset, границы страниц, смену размера, сброс страницы при поиске/фильтре и блокировку переходов при загрузке. После изменения общего компонента проверить оба использующих его списка.

- Для шапки списка проверить единую высоту поиска 32 px в сотрудниках, предприятиях и организациях; сравнить с эталоном положение и ширину поиска, иконку и типографику заголовка/количества. На 390 px поиск должен занимать отдельную строку без лишней колонки. Проверить, что шапка, строки таблицы и подвал доходят до обоих краёв карточки, а отступы остаются внутри ячеек.

- Для компактных шапок предприятий и организаций измерить отступы от внутреннего края карточки и от текста до разделителя по границам блока заголовка. Сверить их и типографику с [компактной карточкой](design/components.md#компактная-шапка-списка). Проверить [три раскладки](design/patterns.md#шапка-и-границы-карточки-списка), в том числе переходы при 640 и 1024 px. При смене значения фильтра поиск и правый край группы сохраняют положение.

- Для бейджей списков предприятий и организаций сверить подписи, цвет текста и заливку в обеих темах. «Действует» использует зелёную палитру, «В архиве» — красную. Проверить строки таблицы и мобильные карточки организаций. [Правило для Badge](design/components.md#карточки-таблицы-и-сообщения).

- Для меню столбцов проверить открытие клавиатурой, несколько переключений подряд, возврат фокуса по Escape и отступы заголовка. Проверить белый фон кнопки в светлой теме и серую подсветку при наведении. Сверить ширину меню по самой длинной подписи и промежуток до галочки, включая «Подключение». Сверить заголовок и ячейки после каждого изменения, сохранение после перезагрузки и отдельную настройку для каждого списка. На узком экране проверить доступность кнопки у таблицы предприятий и карточки сотрудников и организаций. [Оформление меню](design/components.md#настройка-столбцов) · [Правила видимости столбцов](design/patterns.md#видимость-столбцов).

- Профиль аккаунта сверить с карточкой сотрудника при одинаковой ширине и теме. Сравнить ширину карточек, размер аватара, типографику и отступы заголовка и личных данных. На мобильном проверить переход от двух колонок данных к одной. Различия в составе полей и действиях сверить с данными аккаунта и разрешениями. [Эталон карточки сотрудника](design/employees.md#карточка).

- Страницу входа Keycloak сверить с [оформлением Login 01](design/components.md#страница-входа) на 1280 и 390 px. Проверить шапку с логотипом и языком, названия вариантов языка, одинаковую ширину поля в обеих локалях и зазор 1 px между пунктами. Проверить скрытие поля при открытии списка, галочку, навигацию стрелками и возврат фокуса после Escape. Проверить загрузку Onest, выравнивание полей и кнопки, показ пароля, ошибки под полем и переход к двухшаговой регистрации. Сценарии реального входа по телефону и email проверяет `auth-theme.spec.ts`.
