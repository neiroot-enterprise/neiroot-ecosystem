# Аккаунты, экосистемы и доступ

Подтверждено пользовательским планом первого этапа 2 октября 2026 года.

## Аккаунт и экосистема

Один realm Keycloak, глобальная учётная запись и отдельные членства в экосистемах. Нормализованный международный телефон — username, уникальный email допускается при входе. По уточнению пользователя 5 октября регистрация состоит из двух шагов: фамилия и имя обязательны, отчество можно оставить пустым; затем телефон, email, пароль и повтор пароля. В аккаунте сохраняются отдельные компоненты имени и совместимое `full_name` в порядке «фамилия имя отчество». По следующему уточнению пользователя карточка сотрудника хранит отдельные фамилию, имя и необязательное отчество; API создания принимает lastName/firstName/middleName. fullName в ответах остаётся для списка и заголовков. Почтовых проверок и восстановления пока нет.

Гость при открытии сайта сразу переходит на авторизацию Keycloak; со страниц входа и регистрации доступны взаимные переходы. Страница выбора между ними удалена. Приглашение сохраняет собственный сценарий и возврат на `/invite`.

Уточнение интерфейса 5 октября: начальная подсказка телефона +7; российские номера отображаются маской `+7 (999) 000-00-00`, при регистрации и создании сотрудника префикс предзаполнен. При входе можно также вводить email; маска не преобразует email. Явный другой код страны сохраняется. Перед отправкой маска удаляется, требования E.164 и серверные проверки остаются прежними.

Фамилия и имя проверяются профилем Keycloak при регистрации. Автоматическое required action `VERIFY_PROFILE` отключено: существующие и созданные администратором аккаунты с единым `full_name` входят без нового экрана заполнения компонентов имени. Их данные не разделяются автоматически и не перезаписываются.

После свободной регистрации пользователь задаёт название экосистемы. Ядро атомарно создаёт tenant, владельца и его сотрудника; повтор запроса возвращает прежнюю экосистему. Вход по приглашению присоединяет к tenant из серверной записи. Tenant не является предприятием или юрлицом.

| Роль в экосистеме | Смотреть сотрудников | Создавать / приглашать | Назначать admin / user |
|---|---|---|---|
| Владелец (owner) | Да | Да | Да |
| Администратор (admin) | Да | Да | Да |
| Пользователь (user) | Да | Нет | Нет |

Владельца нельзя понизить и нельзя назначить через обычную форму. Роль — запись модуля «Настройки», а не глобальная роль аккаунта в Keycloak. Каждый запрос повторно читает членство и права, поэтому изменение действует со следующего запроса.

## Подключение сотрудника

Карточка принадлежит «Моя компания», членство/роль/приглашение — «Настройки». Фамилия, имя, телефон и email обязательны; отчество необязательно; по умолчанию в форме user. В экосистеме email и телефон уникальны. Связанный аккаунт уникален внутри tenant.

«Задать пароль» создаёт новый аккаунт Admin API с постоянным паролем (8–256 символов), temporary=false. Уже существующий аккаунт подключается только приглашением. Компания не меняет его пароль, телефон, email или глобальное ФИО. Маркер provisioning_id позволяет восстановить повтор создания после сбоя без сброса пароля.

«Пригласить ссылкой» сохраняет карточку и членство без subject. Ссылка привязана к email, действует 7 суток, содержит случайный 256-битный секрет. Для проверки используется SHA-256. По уточнению пользователя 11 ноября готовая действующая ссылка повторно доступна в карточке владельцу/admin. Техническое решение: секрет дополнительно хранится зашифрованным AES-256-GCM с отдельным стабильным ключом ядра `INVITATION_ENCRYPTION_KEY`; шифротекст привязан к tenant, сотруднику, приглашению и хешу. Ключ сохраняется вместе с резервной копией конфигурации, отдельно от БД. Чтение не перевыпускает ссылку и не продлевает срок. При отмене или принятии шифротекст удаляется. Отмена и перевыпуск доступны владельцу/admin; прежняя ссылка при перевыпуске недействительна. Новый пользователь регистрируется, существующий входит, после чего явно принимает приглашение. Email должен совпадать. Роль и tenant берутся из серверной записи, передать их при принятии нельзя. Повтор принятия тем же аккаунтом идемпотентен, другому аккаунту отказ.

Секрет находится во фрагменте /invite#token=…; интерфейс убирает его из адреса, сохраняет только на время OAuth в sessionStorage и отправляет JSON-телом. При успешном принятии секрет удаляется. Письма не отправляются; администратор копирует ссылку самостоятельно.

Следующее уточнение 11 ноября: пока сотрудник ожидает подключения, истёкшая ссылка автоматически заменяется новой на 7 суток через авторизованный POST refresh из карточки. До срока возвращается та же ссылка без продления. Открытая карточка запрашивает обновление по сроку; закрытая — при следующем открытии. Старый токен становится недействительным, само приглашение продолжает действовать. Отмена прекращает автоматическое обновление; отменённое/принятое приглашение refresh не восстанавливает. Истечение и отмена проверяются под той же блокировкой членства, что и принятие, поэтому параллельные запросы не создают несколько новых ссылок и не обходят явную отмену. GET не изменяет данные.

## Серверные границы

BFF: Authorization Code + PKCE S256, случайные state/nonce, одноразовый поток 10 минут, проверка issuer/audience/подписи/nonce ID token. Access/refresh шифруются AES-256-GCM в базе BFF; cookie __Host-neiroot содержит случайный идентификатор, HttpOnly/Secure/SameSite=Lax, срок 8 часов. В базе хранится хеш идентификатора. Мутации требуют точный Origin и X-CSRF-Token. Клиент не получает OAuth-токены.

Если сохранённые токены сессии невозможно расшифровать (например, после смены ключа), BFF очищает её cookie и требует новый вход. Публичный `/api/v1/session` возвращает гостевое состояние, защищённый API — 401. Ошибка чтения БД остаётся 503 и не очищает cookie.

Для каждого параллельного потока входа используется своя HttpOnly/Secure cookie `__Host-neiroot-flow-{state}` на 10 минут. Открытие другой вкладки не заменяет состояние первой; callback удаляет только свою cookie и атомарно потребляет свою запись потока. Прежняя одиночная cookie принимается только при точном совпадении state для переходного обновления. Ошибочный, истёкший или повторный callback отвергается; браузер получает страницу с кнопкой повторного входа, программный запрос — стандартную JSON-ошибку.

Ядро самостоятельно проверяет подписанный JWT с issuer из доверенной серверной конфигурации и audience core-api, затем членство и разрешение. Для новых Keycloak токенов необходим default scope basic с sub. Tenant из URL сам по себе доступа не даёт. Чужой tenant → 403; чужой employee внутри разрешённого tenant → 404.

PostgreSQL: FORCE RLS, core_app без SUPERUSER/BYPASSRLS и прав DDL. app.tenant_id/app.subject/app.invitation_hash задаются set_config(..., true) только внутри транзакции; пул не наследует контекст. Членства текущего subject можно читать для переключателя; публичный lookup ограничен хешем приглашения. Записи company не видны без tenant. Модули не обращаются к чужим таблицам.

Переключатель проверяет членство на сервере, сохраняет выбор в BFF и очищает запросы/кеш предыдущей экосистемы. Подробные права по должности отложены.

## Управление структурой компании

Уточнение 26 октября 2026: все участники экосистемы читают предприятия, отделы, организации, назначения и архив. Только owner/admin создают, изменяют, перемещают, архивируют, восстанавливают и управляют связями. Назначение сотрудника в предприятие или отдел не меняет членство/роль в экосистеме. Снятие назначения не удаляет карточку сотрудника или аккаунт Keycloak.

Ядро проверяет членство и разрешения для каждого запроса независимо от скрытых кнопок. Каждая таблица структуры и связей имеет FORCE RLS; составные внешние ключи запрещают связи между экосистемами и отделами разных предприятий. Архивная структура доступна только для чтения; восстановление — отдельное проверяемое действие. Исключение из действующего предприятия снимает также назначения его архивных отделов.

Уточнение пользователя 4 ноября 2026: пользовательское название tenant — «экосистема». Определение — requirements.md. Технические имена tenant, tenantId и API-маршруты сохраняются; это смена терминологии без изменения границ доступа и данных.

## Сохранность ключа приглашений

Согласованное правило перенесено из AGENTS.md 17 ноября 2026 года. При повторном запуске сохранять существующий INVITATION_ENCRYPTION_KEY. Старые hash-only ссылки невозможно восстановить из хеша. Их разовый перевыпуск требует отдельного согласованного перехода и не выполняется при GET. Порядок хранения ключа и выполненный ранее переход описаны выше и в [development.md](development.md).
