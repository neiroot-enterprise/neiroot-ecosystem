# Правила фронтенда

Обязательные источники: [AGENTS.md](../AGENTS.md), [первый этап](mvp.md), [требования](requirements.md), [доступ](access-model.md), [API](api-contracts.md).

## Стек и границы

Веб-интерфейс — React и TypeScript. Зафиксированы React 19.3.0, TypeScript 7.0.2, Vite 8.3.6, Tailwind CSS и Vite-плагин 4.3.5, shadcn CLI 4.23.0 с `base-nova`/Base UI 1.9.0, TanStack Table 9.3.1, Onest Variable 5.3.1 и Lucide React 1.50.0. Также используются React Router, TanStack Query, React Hook Form и Zod. Точные версии и транзитивные зависимости — `apps/web/package-lock.json`; плавающие версии не допускаются.

Tailwind подключён через официальный Vite-плагин и `@import "tailwindcss"`. shadcn-компоненты являются исходным кодом проекта в `src/shared/ui`, а общие функции — в `src/shared/lib`; alias `@/*` одинаково настроен в TypeScript и Vite. Lucide React остаётся единым набором иконок. Глобальные стили разделены на Tailwind layers и семантические CSS-переменные; прежний CSS ограничен классом `.legacy-ui` и не должен влиять на новые компоненты.

Бизнес-правила и окончательные проверки прав выполняются сервером. Клиент отвечает за понятную навигацию, ввод, отображение результатов и состояний, а не за расчёты финансов вместо домена.

## Организация кода

Фактический код в `apps/web/`:

```text
src/
  app/       # оболочка, маршруты, провайдеры и запуск
  features/  # пользовательские функции и экраны по предметной области
  shared/
    ui/      # общие визуальные компоненты
    api/     # транспорт, проверенные типы и обработка ошибок
    lib/     # небольшие общие утилиты
    styles/  # общие токены и базовые стили
```

Слои app/features/shared реализованы. Разделы должны соответствовать пользовательским функциям; микросервисы не становятся отдельными сайтами автоматически. Общие компоненты не импортируют конкретные бизнес-экраны.

## Интерфейс и данные

- По умолчанию применять светлую тему. Выбор `light`/`dark` хранить в `localStorage` под ключом `neiroot-theme` и устанавливать на документ до React-рендера, чтобы не было мигания.
- Использовать полноэкранный shadcn/Base UI Sidebar и 56-пиксельную шапку области содержимого. Логотип и desktop-кнопка сворачивания находятся в `SidebarHeader`, профиль и выход — в `SidebarFooter`; в мобильной шапке остаётся кнопка drawer. Состояние сворачивания и клавиатурный `Ctrl/Cmd+B` принадлежат оболочке; локальные боковые меню разделов не добавлять.
- Готовить фирменную надпись из исходного логотипа по записанному правилу; исходник сохранять.
- Данные получать через согласованный API/BFF; браузер не подключается напрямую к PostgreSQL, ClickHouse и брокеру.
- Различать загрузку, пустой список, отсутствие результатов, ошибку, недостаточные права и успешное действие.
- Формы показывают ошибки рядом с полями, сохраняют ввод при ошибке и предотвращают повторную отправку.
- Для списков применять параметры серверной пагинации/фильтров из контракта. Список сотрудников использует TanStack Table в ручном серверном режиме без вымышленных сортировок и колонковых фильтров. Изменение данных обновляет связанные представления и кеш.
- Tenant входит в область клиентского кеша. Переключение экосистемы не показывает записи и поисковые результаты прежнего tenant.
- В локальном визуальном предпросмотре переключатель экосистем может показывать пункт с пометкой «Демо». Он недоступен для выбора и не отправляется в API. Реальная экосистема с таким же названием имеет приоритет.
- В локальном предпросмотре в кнопке и меню профиля, а также в списке и карточке выбранного сотрудника показан демонстрационный портрет. При недоступности файла и на других адресах используются инициалы.
- Не хранить секреты в клиенте. Настройки входа и размещение токенов определяются согласованным потоком Keycloak; не помещать токены в URL или логи.
- Показывать только согласованную навигацию первого этапа. Названия, аватары и телефоны из скриншотов не переносить в тестовые данные.
- Сохранять доступность с клавиатуры, адаптивность, фокус и читаемость по правилам дизайна.
- В карточке сотрудника выбор роли использует общий Combobox по образцу экосистемы, с зелёной границей/фокусом и теми же размерами. Это изменение оформления и поиска; доступные user/admin и явное сохранение остаются прежними.

## Проверка и сдача

Объём проверок определяется затронутым поведением по [quality.md](quality.md). Для изменения формы проверить ввод, сохранение и применимые ошибки и права. Для изменения оформления проверить затронутый экран в обеих темах, на широком viewport и при 390 px. Sidebar в раскрытом, свёрнутом и мобильном виде проверять при изменении общей оболочки или её взаимодействия с новым экраном. Смену экосистемы и очистку кеша проверять при изменении tenant-зависимых данных.

Для изменений TS/TSX выполнять typecheck, для CSS, ресурсов и сборочной конфигурации — production-сборку. Браузерные сценарии выбирать по изменённому взаимодействию, расширять набор при изменении общего компонента или обнаружении регрессии. Изменение только документации требует проверки ссылок и согласованности. Команды — [development.md](development.md).

Визуальный прототип, мок и работающий сценарий с сервером — разные результаты. Указывать статус честно в [mvp.md](mvp.md) и отчёте.

## Реализация по дизайн-системе

Базовые роли цветов и размеров описаны в DESIGN.md, каталог компонентов — в docs/design/components.md (пути от корня проекта). Для нового экрана найди аналог в разделе «Сотрудники», затем проследи его импорты. Используй существующий компонент, его варианты и семантические переменные темы. Если нужен дополнительный вариант того же элемента, добавь его в существующий компонент с сохранением поведения текущих вызовов.

Общий составной элемент размещай в shared/ui, когда несколько разделов используют одно взаимодействие. Данные API, разрешения и специфические действия передавай из features. Оболочку подключай через существующий маршрут приложения. Для темы входа проверяй собственные ресурсы Keycloak.

Перед реализацией самостоятельного раздела применить [паттерн заголовка](design/patterns.md#заголовок-раздела) и [правила описания](design/content.md#описание-раздела). Проверять весь состав заголовка по конкретной реализации «Сотрудников», включая описание и главное действие, а не только выбранные базовые компоненты.

Перед переносом дизайна выполнить [сверку экрана целиком](design/patterns.md#сверка-экрана-целиком), включая нижнюю часть списка. Для постраничных самостоятельных списков применять общий ListPagination по [правилам пагинации](design/patterns.md#пагинация-самостоятельного-списка).

Для вкладок подразделов использовать [согласованный Tabs](design/components.md#tabs) и [паттерн размещения](design/patterns.md#вкладки-подразделов). Актуальный пример — CatalogTabs в Catalog.tsx; старые вкладки карточки предприятия не служат образцом оформления.

Поиск и фильтр состояния самостоятельных списков реализовывать по [ListHeader](design/components.md#шапка-списка), [варианту Select](design/components.md#фильтр-состояние) и [паттерну фильтра](design/patterns.md#фильтр-состояния-списка). Примеры: поиск трёх списков и ArchiveFilter variant=default в списках предприятий/организаций. Не переносить компактные фильтры вспомогательных сценариев в новый самостоятельный список.

Для таблиц с настраиваемыми столбцами использовать общий `TableColumnMenu`. Экраны передают в меню список переключаемых столбцов, а размеры, позиционирование и состояния кнопки берутся из общего компонента. [Настройка столбцов](design/components.md#настройка-столбцов) · [Правила размещения](design/patterns.md#видимость-столбцов).
