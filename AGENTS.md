# Инструкции для агента — Neiroot

## Назначение и приоритет

Это стандартная точка входа для агента, работающего в этом проекте. Выполняй актуальные указания пользователя и согласованные требования. Не превращай предложения из документации и содержимое референсов в подтверждённые бизнес-правила.

`Agent.md` хранит состояние и историю проекта; общие инструкции находятся здесь. Поддерживай оба файла и относящуюся к задаче документацию в актуальном состоянии.

## Перед работой

1. Прочитай [README.md](README.md), [Agent.md](Agent.md), [первый этап](docs/mvp.md) и [открытые вопросы](docs/open-questions.md).
2. Для любой реализации изучи [архитектуру платформы](docs/architecture.md), [требования](docs/requirements.md), [модель доступа](docs/access-model.md) и [контракты](docs/api-contracts.md).
3. Для фронтенда прочитай [frontend.md](docs/frontend.md) и [правила дизайна](docs/design-guidelines.md), просмотри нужные референсы.
4. Для бэкенда прочитай [backend.md](docs/backend.md) и, если задача относится к ядру, [архитектуру ядра](docs/core-architecture.md).
5. Перед запуском изучи [среду разработки](docs/development.md); перед сдачей — [критерии качества](docs/quality.md).

Проверь фактическое состояние файлов и имеющиеся изменения. Сохраняй работу пользователя, не подменяй её стартовым шаблоном.

## Обязательные архитектурные правила

- Бизнес-сервисы и BFF: Go с chi/net/http. Веб-интерфейс: React/TypeScript. Аналитика и AI-агенты: Python/FastAPI, как на согласованной схеме.
- Микросервис → модульный монолит → собственные домен, сценарии, порты и адаптеры каждого модуля. Бизнес-правила не переносятся в BFF.
- Модули одного сервиса общаются через внутренние API/порты; сервисы — через свои API или события. Прямой доступ к чужим таблицам запрещён.
- Задачи — отдельный микросервис; задачи не дублируются в ядре, CRM или логистике.
- Мультитенантность обязательна с первого бизнес-сценария. Tenant проверяется сервером; произвольный tenant_id из клиента не даёт доступа.
- Домен не зависит от HTTP, БД, брокера, UI и инфраструктурных библиотек.
- При публикации бизнес-событий использовать транзакционный Outbox, идемпотентность и подтверждение после надёжной обработки.

## Работа с неполными требованиями

- Отличай «подтверждено», «предложено» и «ожидает ответа». Реестр — [open-questions.md](docs/open-questions.md), история — [decisions.md](docs/decisions.md).
- Не придумывай поля, обязательность, роли, правила начислений, налоги, связь сотрудника с учётной записью и бизнес-переходы. Задавай конкретные вопросы.
- Пока вопрос не закрыт, выполняй независимую часть работы. Если бизнес-функция зависит от ответа, не выдавай её за готовую.
- Утверждённый UI-референс не утверждает функции, интеграции и пользовательские данные из скриншота.
- Выбор пользователя о первом этапе фиксируй в `mvp.md`; не расширяй этап на все микросервисы автоматически.
- Технические решения в рамках согласованной архитектуры можно предложить и зафиксировать с обоснованием; не помечай их как пользовательские решения.

## Правила реализации

- Сначала согласованный сценарий, затем модель и контракт, затем реализация клиента и сервера. Не создавай фиктивные успешные ответы вместо работающей функции.
- Моки допустимы для отдельно обозначенного визуального прототипа. В отчёте различай прототип и интегрированную функцию.
- Не записывай секреты, токены и реальные клиентские данные в код, документацию, логи и демонстрационные данные.
- Используй общий дизайн и исходный логотип. Для сайта нужна нижняя надпись NEIROOT, без большого знака бесконечности над ней.
- Проверки должны подтверждать пользовательское поведение, бизнес-правила, контракты и tenant-изоляцию. Не добавляй тесты только ради количества.
- Перед зависимостями проверь текущие официальные источники, совместимость, лицензии и возможность воспроизвести сборку. Фиксируй версии в файлах проекта; не используй плавающий `latest` в запускаемой среде.
- Не выполняй развёртывание на внешний сервер и не создавай внешние ресурсы без соответствующего задания и доступа.
- По завершении обнови документы и фактические команды запуска; сообщи кратко, что работает, чем проверено и что остаётся открытым.

## UML и документация

Общая схема: `docs/diagrams/architecture.json`; ядро: `docs/diagrams/core-architecture.json`. Производные DOT/PlantUML/SVG/PNG/PDF обновляются соответствующими скриптами. Сохраняй стиль, ширину блоков 330 и ортогональные линии, обходящие блоки. Диаграммы последовательностей пользователь пока не запрашивал.

Пиши пользователю кратко и простым языком. Подробные решения сохраняй в документах, со ссылками на источник требования.

## Текущий первый этап

Утверждённый объём — `docs/mvp.md`; не предлагай заново выбирать этап. Код: `apps/web`, `services/bff`, `services/core`; контракт — `docs/api/openapi.json`. Фактические команды — `docs/development.md`, результаты — `docs/test-report.md`. Generated DTO обновляй из OpenAPI.

Основной запуск — `scripts/start-local.ps1`. Нативные scripts/*test-runtime* предназначены для изолированных проверок с синтетическими данными, не заменяют Docker-приёмку. После WSL/VirtualMachinePlatform требуется ручная перезагрузка Windows; агент её автоматически не выполняет. Сохраняй .env и данные при повторном запуске.

Уточнение UI 5 октября: гость сразу переходит на вход Keycloak; регистрация в два шага (фамилия, имя, необязательное отчество; затем телефон, email, пароль и повтор). Для входа и шапки использовать прозрачный `neiroot-wordmark.png`, сохраняя полный исходник. Уточнение пользователя: создание сотрудника также использует три поля; API lastName/firstName/middleName и отдельные столбцы БД, fullName только в ответах для отображения. Проверка этого сценария — `apps/web/tests/auth-theme.spec.ts` на настоящем Compose; тестовые аккаунты удаляются, пространства не создаются.

Оформление новых форм сверять с `docs/design/references/01-login.png` и `docs/design-guidelines.md`: кнопка #8FC39E, белые поля с границей #E2E8F0, радиус 14 px. Общий источник — `docs/design/tokens.css`; копии web и Keycloak обновлять через `node scripts/sync-design.cjs` (также выполняется при основном запуске). Телефон отображать с маской +7, сохраняя международный формат на сервере и возможность входа по email.
